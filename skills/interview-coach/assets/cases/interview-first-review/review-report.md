## 本次主要发现

## 1. RAG 的进一步探索

**来源**：133.4-213.2 秒 · 共 2 个复盘版本，以下为第 2 版。

**题干归纳**：你已经提到 BM25、语义相似度、混合检索、查询改写、意图识别，除了这些之外，还有什么其他技能或经验可以聊一聊？

**原回答短摘（ASR，未听校）**：

> 嗯，比如说rag吧，其实我觉得嗯其实我们最开始的rag哈，我觉得分三级吧，第一级它就是一个简单的查询，就一条链路直接查询检索增强，然后再到我们实际工业落地的这个项目，它可能就是再去查询改，就是再去检索增强的时候加入一些策略，就是多了照顾也好，或者说那些策略也好，它都是把rag去作为一个让它生成的更好嘛，然后我觉得再往上可以转向一个。就是rag agent好吧……

**教练反馈**

层次感是有的：三级递进加知识图谱，说明脑子里有地图。问题在三条线混着讲，且没说清哪一级是真落地的。"工业落地的这个项目"后面接"它可能就是"，把已做的降级成假设，听者拿不准边界。建议先报层级归属再展开。注意：原回答无法确认你实际做到第几级、哪级已用、哪级未落地，上一版改写代你确认了进度，本版改为留空待你补充。

**建议改写／表达模板（非原话）**

【表达模板，待本人补充】这条线我分三级看：一级是单链路检索增强；二级是在检索增强里加策略，混合检索、查询改写、意图识别属这一层；三级是我理解的 agent 化，把检索和意图识别做成工具，由外层编排统一控制。我实际做到第【＿】级，其中【＿】已有实践，【＿】目前只是设想或评估方向。知识图谱是针对多级溯源的想法，进度【＿】。具体策略和取舍我再展开。

**追问练习**

先把模板里的四个空按真实情况填上，再脱稿讲一遍：第一句报做到第几级，最后一句区分实践与设想，不出现"可能是""可以去探讨"。

## 2. 文档清洗项目难点

**来源**：251.6-435.5 秒 · 共 2 个复盘版本，以下为第 2 版。

**题干归纳**：你过往项目以 RAG 和多 agent 为主，能不能挑一个你觉得比较复杂的项目详细介绍一下，有什么难点、怎么解决的？

**原回答短摘（ASR，未听校）**：

> 首先我觉得，其实做一个RAG系统的话，前置部分哈，就是文档切分那一部分是很重要的，就是文档数据的清洗。然后至于当时数据去怎么清洗呢，其实我们是做了一些工作的哈。直接跟您说结果吧，我们最后用的是一个Docling，就是用的这个Python的一个开源库。然后用这个库去对文档做了一些。嗯，算是数据管道的清洗吧。因为可能我们比如说PDF吧，复杂一点哈，你可能会有一些……

**教练反馈**

内容实在，PDF、Word、Excel 都有做过的痕迹，问题在不分主次，像在报进度。开头说"文档切分很重要"，后面一直在讲解析和清洗，分块一句话带过。建议挑一个（如图文混排 PDF）作主案例，按问题、做法、验证三层讲，其余一句带过。上一版把"看检索片段是否完整可读"写成了亲历判断，原回答无此内容，本版改为待补充的验证方法。ASR"创客/创卡"疑为 chunk，属转写误差。

**建议改写／表达模板（非原话）**

我挑图文混排 PDF 举例。难点是解析质量直接决定后续分块和检索：通用解析下，单页表格、左右双栏容易读错顺序，chunk 边界随之变乱。做法是用 Docling 生成结构化文档，拿到单页文字与图片位置；跨页断开处用正则和序号规则接回；含图片页面再走一遍多模态重解析，不依赖 OCR 准确率；清洗后按结构切块。可补充的验证方法（尚未提供实测结果）：看检索返回的片段是否完整可读。Word 结构规整；Excel 带表头逐行入管道，复杂表格另写专用解析。

**追问练习**

只讲一个难点，90 秒：现状问题 → 具体做法 → 验证方式。验证部分明确说"这一点我还没实测数据"，不出现"然后就""包括说"。

## 3. 海量用户表设计

**来源**：953.6-1029.0 秒 · 共 1 个复盘版本，以下为第 1 版。

**题干归纳**：假如我们建一张用户表，用户非常多，可能有 10 亿用户，相关数据也非常多，除姓名、年龄、账号、手机号、邮箱，还包括个人简介、个性签名、头像、爱好兴趣等，字段非常多、数据量非常大，这张表应该怎么设计？

**原回答短摘（ASR，未听校）**：

> 首先我觉得呃就是这种情况下肯定涉及到一个分不分表哈，然后这个是肯定要做的，因为你数据量这么大的话，你一旦去查的时候就。就去做一个分库分表吧，然后另外如果说字段多的话，也要看它有多多哈。然后如果说我觉得你把分库分表的边界，就是就是首先它字段多的时候，比如说我们在查某一个的时候，比如说把索引给建好了哈，减少回表。你哪怕是分库的那个库数据相对多一点的话，只要我们回……

**教练反馈**

方向都有，但顺序有点问题：一开口就"肯定要分"，后面又重复"做个分股分表"，把结论放在依据前面，听着像背结论。10 亿只是总量，是否拆分要看单表体量、读写 QPS、查询能否命中索引，这些不先问就给方案会显得没验证。另外是建议（非你的原话）：索引和宽表拆分解决的不是同一件事——索引让单表查询少读数据、少回表，宽表拆分是把低频大字段挪走、缩短主表行长；两者都能减压，但都不替代按数据量做分片。ASR"分股"疑为分库，属转写误差。

**建议改写／表达模板（非原话）**

我先问清两件事：单表数据量和主要查询方式。10 亿是总量，如果大字段拆分加索引就能支撑高频点查，不一定马上分片。字段多，我把低频大字段（个人简介、签名、头像）拆到扩展表，主表只留高频轻字段，减少行长和 IO；高频查询建好索引，尽量不回表。数据量和写入继续涨到单机扛不住，再按用户 ID 分片，用分布式 ID 保证唯一，片键和路由按业务查询来定，避免跨片查询。分表解决单表体量和写入，索引和拆宽表解决查询效率，层级不同。

**追问练习**

60 秒：先讲"我会先确认单表数据量、QPS、查询方式"，再给分层方案，最后一句讲清分片、拆表、索引各解决什么。全程不出现"肯定要分"。
